② 五种操作的记录 真机（或设备模式）实测填写

单击

touchstart → touchend → click

没有 touchmove；click 在 touchend 之后补发，间隔约 0～300ms。

向上拖动

touchstart → touchmove × 30± → touchend → click

touchmove 连续不断（约 60 次/秒），每条的坐标都在变；拖得越久，次数越多。

向左快速滑

touchstart → touchmove × 8～15 → touchend

时间短、事件少但位移大；位移过大或触发滚动时，浏览器可能吞掉最后的 click。

双指触摸 （可选）

touchstart(1 指) → touchstart(2 指) → touchmove × N → touchend(→1 指) → touchend(→0)

每根手指按下都会各触发一次 touchstart；move 时 e.touches.length === 2；抬起一根时 touches 变 1，属于“部分离开”。

长按后抬起

touchstart →（静置 600ms）→ touchend → click

静置期间没有 move；长按计时器在 touchend 里被清掉，所以“长按”不能靠 setTimeout 孤零零地等。

③ 三个思考问题与答案 验收必答

Q1.一次拖动里 touchmove 大约触发多少次？和距离有什么关系？

次数由“时长 × 屏幕刷新率”决定，不由距离决定。touchmove 是跟着屏幕刷新逐帧派发的，60Hz 设备约每 16.7ms 一次，也就是每秒 60 次左右（120Hz 设备翻倍）。实测一次 0.5 秒、200px 的拖动大约 25～30 次；同样 200px 但慢慢拖 1.5 秒，就会有 80～100 次。

所以“距离越大 move 越多”只是表象：慢拖时距离和时间同时增长，次数才跟着涨；快速甩动距离很大，但时间短，事件次数反而少。每个 touchmove 的坐标差就是这一帧的跟手位移，帧率越高、次数越密，跟手就越顺滑。

一句话：move 的次数 ≈ 拖动时长 ÷ 16.7ms，距离只影响“每次位移的大小”。

Q2.click 出现在 touchend 之前还是之后？

之后。完整顺序是：touchstart → touchmove × N → touchend → click。click 是触摸序列结束后浏览器补发的“兼容鼠标事件”，历史上还会为了判断双击而等待约 300ms。

如果 touchend 和 click 里都写了逻辑，就会出现“点一次执行两次”。三种处理方式：① 只监听一套，二选一；② 在 touch 处理里 e.preventDefault()（但会连带影响 input / a 的默认行为）；③ 加 touch-action: manipulation 去掉 300ms 延迟，让两者时序更可预期。

本次四个任务全部只走 touch 一套逻辑，所以不会重复执行。

Q3.如果把 touchend 换成 touchcancel，会发生什么？

正常抬手时，什么都不会发生。touchcancel 只在触摸被系统“打断”时派发：来电、通知横幅、系统弹窗、手势返回、切后台、页面被隐藏等。正常抬起手指只会触发 touchend。

所以换掉之后：滑动判定的代码永远不跑（卡片不切换）、长按定时器不会被清掉（松手后仍然弹出长按菜单）、拖动状态也不会复位（下次按下还算旧起点，出现“跳一下 / 卡住”）。

正确做法是两个都写：touchend 做正常收尾（判断方向、取消定时器、吸附边界），touchcancel 做同样的“清场”（复位状态、清定时器、回弹），并让二者调用同一个 reset 函数。本次四个页面都补了 touchcancel。

口诀：touchend 是“正常结束”，touchcancel 是“被打断”，清理逻辑必须两边都覆盖。
